# 개인 웹 프로젝트 디자인 가이드

목표는 서비스 목적에 맞는 화면을 만들고, 화면이 늘어나도 같은 규칙으로 수정할 수 있도록 하는 것입니다. Figma를 사용하거나 코드로 바로 UI를 구현하는 두 방식 모두에 적용합니다.

## 1. 먼저 목적과 범위를 정하기

[프로젝트 브리프](project-brief-template.md)를 채웁니다.

- 누가, 어떤 상황에서, 어떤 문제를 해결하려고 사용하는가?
- 사용자가 가장 먼저 끝내야 할 행동은 무엇인가?
- 이번 MVP에서 확인하려는 가설은 무엇인가?
- 반드시 필요한 기능과 이번에 만들지 않을 기능은 무엇인가?

기능 목록보다 핵심 사용자 흐름을 먼저 정합니다. 예: 목록 탐색 → 상세 확인 → 신청 → 결과 확인. 기존 프로젝트라면 실제 화면과 컴포넌트부터 조사합니다.

## 2. 화면 목록과 정보 우선순위

핵심 흐름에 필요한 화면부터 만듭니다. 처음에는 약 3~5개를 출발점으로 삼되, 숫자에 맞추려고 불필요한 화면을 추가하지 않습니다.

각 화면에 목적, 가장 중요한 정보, 주 행동, 보조 행동, 진입·이탈 경로를 적습니다. 긴 목록의 검색·필터·페이지 이동도 실제 사용 목적에 따라 정합니다.

## 3. 시각적 방향 정하기

- 참고 사이트 1~3개와 참고할 이유를 적습니다.
- 분위기, 정보 밀도, 타이포그래피, 색상 사용 정도를 구체적으로 정합니다.
- 참고할 특징과 피할 특징을 함께 적습니다.
- 브랜드 로고와 자산을 그대로 복사하지 말고 사용 권한을 확인합니다.

AI에게는 “예쁘게”보다 “모바일에서 목록을 빠르게 훑고 주 행동을 찾기 쉽게”처럼 사용 목적을 설명합니다. 목표 회사나 특정 유행을 모든 프로젝트의 기준으로 고정하지 않습니다.

## 4. 디자인 토큰을 실제 구현과 연결하기

최소한 다음 항목을 정의합니다.

| 항목 | 정할 내용 |
|---|---|
| 색상 | 배경, 표면, 본문, 보조 텍스트, 테두리, 주 행동, 성공·경고·오류 |
| 글자 | 글꼴, 크기, 굵기, 줄 높이, 제목과 본문의 위계 |
| 간격 | 반복해서 사용할 간격 단계와 화면 바깥 여백 |
| 형태 | 둥글기, 테두리 두께, 그림자 |
| 레이아웃 | 콘텐츠 최대 너비, 그리드, 화면 크기에 따른 변화 |
| 동작 | 전환 시간, 포커스 표현, 모션 감소 설정 |

값 자체보다 이름과 역할을 일관되게 유지합니다. Figma는 Variables·Text Styles에, 코드는 CSS 변수·프로젝트 테마 설정에 반영합니다. 이미 토큰 체계가 있으면 확장해서 사용합니다.

다음은 문법 예시일 뿐, 모든 프로젝트에 고정할 기본 디자인은 아닙니다.

```css
:root {
  --color-background: #ffffff;
  --color-text: #172033;
  --color-primary: #1d4ed8;
  --space-2: 0.5rem;
  --space-4: 1rem;
  --radius-control: 0.5rem;
}
```

## 5. 반복되는 UI를 공통 부품으로 만들기

실제로 여러 곳에서 쓰이는 버튼, 입력창, 카드, 내비게이션, 모달 등을 공통화합니다. 아직 필요하지 않은 범용 컴포넌트를 미리 잔뜩 만들지는 않습니다.

- 버튼: 주 행동·보조 행동, 크기, 비활성, 로딩 상태.
- 입력창: 라벨, 도움말, 필수 여부, 오류 메시지, 포커스.
- 카드·목록: 제목, 핵심 정보, 보조 정보, 행동의 일관된 배치.
- 모달·메뉴: 열기·닫기, 키보드 접근, 포커스 복귀.

Figma에서는 Auto Layout, Component, 필요한 Variants와 Instance를 사용합니다. 코드에서는 공통 컴포넌트와 명시적인 속성으로 구현합니다. 색상·간격을 화면마다 임의의 값으로 반복 지정하지 않습니다.

## 6. 정상 화면 밖의 상태도 설계하기

화면별로 실제 필요한 상태를 점검합니다.

- 로딩 중이며 기다리는 이유가 보이는가?
- 데이터가 없을 때 다음 행동을 안내하는가?
- 검색 결과 없음과 최초 데이터 없음이 구별되는가?
- 입력 오류·요청 실패를 이해하고 재시도할 수 있는가?
- 완료 결과와 중복 제출 방지가 명확한가?
- 로그인·권한에 따라 달라지는 화면이 필요한가?

## 7. 반응형과 접근성

- 모바일에서 주 행동과 중요한 정보가 가려지지 않게 합니다.
- 실제 콘텐츠로 작은 화면·큰 화면, 긴 제목, 긴 한국어 문장을 확인합니다.
- 키보드만으로 이동·선택·닫기가 가능하고 포커스가 보이게 합니다.
- 입력 라벨과 의미 있는 HTML 구조를 사용합니다.
- 색만으로 상태를 전달하지 않고 텍스트나 아이콘을 함께 사용합니다.
- 대비, 확대, 터치 대상, 모션은 적용할 접근성 기준에 맞춰 확인합니다.

## 8. 완료 전에 확인하기

- 핵심 사용자 흐름을 처음부터 끝까지 직접 따라갈 수 있는가?
- 같은 역할의 UI가 같은 토큰과 컴포넌트를 사용하는가?
- 로딩·빈 화면·오류 상태가 실제 구현에 연결되어 있는가?
- 모바일·데스크톱에서 실제 실행 화면을 확인했는가?
- 디자인 기준과 코드 구현이 어긋난 부분이 기록되어 있는가?
- 확인하지 못한 부분과 다음 수정 사항을 구분해서 남겼는가?

완료 보고에는 변경한 화면과 실제 확인한 범위를 적습니다. 스크린샷만으로 API 동작이나 키보드 접근성이 검증됐다고 말하지 않습니다.

## AI에게 전달할 프롬프트

```text
프로젝트 브리프와 기존 UI 코드를 먼저 읽어줘.
핵심 사용자 흐름, 화면별 주 행동, 시각적 방향을 정리하고
필요한 디자인 토큰과 공통 컴포넌트를 제안해줘.
기존 규칙을 우선 사용하고, 아직 결정되지 않은 것은 제안으로 표시해줘.
합의한 범위 안에서 구현한 뒤 반응형과 필요한 화면 상태를 확인해줘.
```
